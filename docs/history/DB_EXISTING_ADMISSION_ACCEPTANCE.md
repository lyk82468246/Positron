# Existing local DB admission acceptance

This record covers `PDb_VerifyExistingLocalUtf8` and additive `PDb_OpenExistingLocalUtf8`, not Runtime READY registration or application launch. Stable calls and limits are in the [DB README](../../positron_db/README.md#verifying-an-existing-local-database-without-writes).

## Read-only implementation and failure boundary

The DLL opens a private SQLite connection with READONLY/FULLMUTEX and no CREATE, and never invokes metadata initialization or identity binding. One read transaction checks a real generated metadata table, canonical TEXT local mode, exact TEXT identity and strict expected schema; BLOB checks precede text coercion. It closes before returning, publishing no handle or authority. Fixed connection/query/VM limits are inspection guards, not native-I/O or whole-SQLite memory deadlines. The 16-MiB page guard measures logical pages, not trailing physical bytes.

Missing/inaccessible paths fail without creating them. Empty/foreign/malformed or mismatched metadata fails without adopting, initializing, migrating or deleting data. The progress interrupt is disabled before failure cleanup, and exhaustion is categorized as LIMIT rather than cancellation. A successful result remains a point-in-time observation; callers must not use a later old CREATE-capable open as a replacement for verified existing-handle admission.

VM exhaustion, extreme schema resources, logical-page maximum and actual hot-journal recovery failures are not claimed as exercised. Physical FULL/I/O/power-loss work remains under its existing user-directed suspension.

## Writable existing-handle admission

The writable entry uses the same exact v1 identity/schema inputs and ErrorInfo ABI. Its read-only snapshot remains alive while a no-CREATE writable connection acquires BEGIN IMMEDIATE and independently validates its own metadata, identity and schema. It rejects SQLite read-only fallback and non-DELETE journal mode, never initializes metadata or claims an identity, then commits the empty admission transaction and publishes the idle actual handle. Native containment/anti-replacement and installation coordination must remain held until that handle closes; the DB entry does not implement a filesystem sandbox or grant author services.

Each inspection connection has a 100000-unit VM budget and fixed length/depth/variable/VM limits. The returned connection uses the existing authorizer/progress mechanism, FULL synchronization, foreign keys and a logical 16-MiB page quota computed from the existing page size. There are at most two admission connections, not a claimed total SQLite-memory or native-I/O deadline. The retained read snapshot prevents a concurrent SQLite commit during admission and refuses hot-journal recovery requiring writes before the writable open. Actual hot-journal/fault injection and extreme-resource cases remain unexercised; the existing FULL/power-loss suspension remains intact.

TEST1382 reuses all seventeen file cases with writable admission, including two attempts per case and exact native before/after bytes and journal absence. The OS-readonly case must now fail rather than publish a fallback read-only handle. Additional cases hold a competing BEGIN IMMEDIATE reservation and require BUSY/NULL output, change identity after an earlier successful probe and require rejection, then restore the fixture and check successful idle admission, restricted INSERT, close/reopen and exact stored value 42. Invalid ErrorInfo version preserves its canary, and a missing handle output fails before I/O. Only private fixture files are created/removed.
