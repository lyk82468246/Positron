# Installed page queue and Browser bridge acceptance

This record covers READY installed storage using the existing Runtime page queue and Browser controlled service bridge. It is not final installation COMMIT, an EXE installed-app entry, PXI publication or a browser security sandbox. Stable calls and ownership are in [the installed queue contract](../../positron_runtime/INSTALLED.md#binding-installed-page-queues-to-browser).

## Product changes and boundaries

QueueCreate now admits installed storage only after fresh READY registration and instance-cancel checks, with no partial queue output on failure. ProcessOne retains the existing restricted SQL/JSON execution path, including registration refresh before SQL. Runtime owns these decisions; test_host only supplies native facts, callbacks, files, thread/event scheduling and assertions. No Browser/Core/EXE product implementation changes.

A request cancellation is separated from instance cancellation. A per-job QueueCancel or page QueueRevoke discards that job/page result without retiring healthy installed storage or siblings. An observed instance cancel, registry loss/change or unusable storage failure instead retires the instance and revokes all sibling queues, dropping waiting/unclaimed results and requesting cancellation of a running job. Native callbacks cannot close a queue while its storage/parent operation is active, including an idle sibling. The DB-unusable/rollback-fault branch follows this same retirement path but has not been physically fault-injected; existing suspended FULL/power-loss work remains suspended.

The existing copy ABI, 4 queues × 8 slots, 4096-byte request/result limits and SQL VM budgets remain fixed. Combined revision/storage/SQL work, four queue allocations and reserve fit the existing compile-time 1280-KiB Runtime-owned bound; SQLite/CSP/native memory is excluded. No new public structure, export, worker or message pump is introduced.

The UI must observe worker-notified retirement and revoke Browser services on the session owner. QueueGetInfo is a synchronized copy, not a registry I/O operation or instantaneous external-revocation oracle. UI access must stop before worker Close; the queue remains alive for Browser cancellation callbacks. Revoke discards Browser callback references without invoking JS. A committed write whose result is discarded is never replayed. Registry coordination is still required and does not create a transaction spanning registry/application databases.

## Device corpus

TEST1384 uses a real native worker and test-host UI/Browser owner. Each of six scenarios prepares/approves immutable resources, verifies the installed revision, opens a private identity-bound existing DB, and creates bounded page queues on the worker. Browser submit only copies JSON; mutation of the source JS object after Submit cannot replace the admitted INSERT. Worker execution commits once, UI Complete only copies, and owner Pump delivers the typed changes result exactly once. Stale/replayed request tags are rejected and empty Take preserves its output canary.

Scenarios then exercise: running individual cancellation followed by successful SQL on the same healthy instance; registry revocation before queued writes; a generation change detected by new QueueCreate while one result is unclaimed and a sibling write waits; instance cancellation before processing; page revocation after COMMIT with a sibling still usable; and instance cancellation before granting a new queue. Both sibling queues' waiting/running/completed counts converge on instance retirement, Browser waiting references are revoked, and late Complete cannot resurrect them. Worker close order and native location/root/registry balances are checked. A cold existing-only native read independently asserts exact final row counts (1/1/2/1/3/1), proving which commits survived and that dropped results were not replayed.

The fixture also checks four queues/fifth refusal, duplicate page rejection, wrong-thread processing, storage/revision retention and callback-close guards. TEST1383 now verifies the supported installed queue lifecycle in place of its earlier UNSUPPORTED boundary. Existing development queue/SQL regressions remain selected. The native cancellation checkpoint deliberately uses test-only event barriers to schedule the race; production callbacks remain atomic flag readers, not blocking rendezvous or UI pumps. No live DB/Browser handle crosses ownership threads. If a failed worker cannot join, the fixture retains its state rather than freeing memory still in use.
